After appropriate **owner-admin Firebase application credentials** are available in the uncaptured GMKtec account, run the existing project dependencies in a **private, interactive PowerShell** session from `private-app`:

```powershell
node tools/provision-production-members.mjs "<private-absolute-production-config.json>"
```

This one-time command is restricted to the existing Justelle production project, site and separate qualification project. It checks both emails and accounts **before writing**, refuses to grant membership to any previously existing unverified account, creates two new distinct Auth users with unverified emails, adds the room-scoped claims and unique permanent person IDs, and creates the room last. It never replaces an existing room or authorship mapping. Rerunning against exactly the same verified room is read-only; conflicting or partially completed state requires private owner inspection, not automatic deletion of historical records. A failure before room creation attempts to clean up only the new unprivileged users; a possibly committed room write is never undone by blindly deleting users. Output reports only generic two-member success/failure, never identities or secrets.

**Credential boundary:** `firebase login` or `gcloud auth login` does not by itself prove Firebase Admin SDK user-management access. Use existing qualified owner-admin Application Default Credentials, following [Firebase Admin SDK local authentication guidance](https://firebase.google.com/docs/admin/setup#test-with-gcloud-end-user-credentials) where applicable. If no safe authenticated owner-administration path is available, leave setup blocked and report that exact access requirement.

Once the accounts and room are actually read back, install the **same** protected production config in the established `justelle-production` GitHub Actions environment, using an owner-controlled secret input. Keep the private local file out of the repository and do not publish it as a workflow artifact. Auth/membership setup does not turn on the app, AI, scheduled backup or any readiness flag. Ensure genuine production encrypted recovery is independently restorable **before real adventure content is admitted**.

Create a private, Object Lock-enabled B2 bucket with a default governance retention period and lifecycle policy agreed within the approved operating allowance. Before uploading, the backup job verifies the bucket reports **GOVERNANCE** mode and a positive supported default period (1–3,000 days or equivalent supported years); a merely enabled lock or COMPLIANCE default fails closed. After each upload it also reads the **exact uploaded object's retention**, specifying its returned version ID when available, and rejects anything other than GOVERNANCE with a future retain-until timestamp. These source-level checks are **not** proof of real B2 retention, independent remote restoration or account setup until hosted qualification succeeds. The uploader key must be restricted to that bucket and prefix: upload/read objects, inspect bucket retention (`readBucketRetentions`) and inspect individual file retention (`readFileRetentions`), with no delete permission, `writeFileRetentions` or governance bypass. Store only encrypted `.jmb` files. Keep a separate offline copy of the 32-byte recovery key outside Firebase and B2; verify its custody before real content. The automated key copy is a Secret Manager secret available only to the backup identity. The B2 account cannot decrypt the archive.


### Backblaze B2 first-time account handoff

If the signed-in Backblaze account shows only **Computer Backup** and no **Buckets**, check **My Settings → Enabled Products** and enable **B2 Cloud Storage** on that existing account before provisioning anything. After accepting the applicable B2 terms, use **B2 Cloud Storage → Buckets**, not Computer Backup. Do not assume that an existing Computer Backup subscription already enables B2. [Backblaze's B2 enablement steps](https://www.backblaze.com/docs/en/cloud-storage-enable-backblaze-b2) and [bucket creation guide](https://www.backblaze.com/docs/cloud-storage-create-and-manage-buckets) are the current console references; if the product is already enabled, reuse it instead of creating another account.

For the initial **fictional qualification** target, create a globally unique bucket such as `justelle-qualification-backups` (add a neutral suffix if taken), select **Private**, and enable **Object Lock** at creation. Save the displayed S3 endpoint privately. Configure and read back **default GOVERNANCE retention of 30 days** before the first upload. An Object Lock-enabled bucket without **default** retention is not qualified: its next object may be unprotected. Do not use COMPLIANCE as an improvised substitute. Keep the production target and retention decision separate, following the approved backup policy. See [Backblaze Object Lock](https://www.backblaze.com/docs/cloud-storage-object-lock).

**Trusted Windows CLI note:** If the B2 Python package is present (`py -m pip show b2`) but `b2.exe` was not installed on PATH, use `py -m b2._internal.b2v5` instead of the `b2` prefix in the illustrative commands below. This runs Backblaze's installed version-bound v5 entrypoint without reinstalling software or changing PATH; the owner-only bootstrap script invokes it directly on Windows. A Backblaze browser sign-in does not establish local CLI authorization: check `py -m b2._internal.b2v5 account get` privately and never paste its account metadata into a public transcript. If Windows PowerShell blocks `gcloud.ps1`, use Google's installed `gcloud.cmd` launcher rather than changing PowerShell execution policy. The bootstrap captures credential-bearing output in memory only, and the printed recovery key is entered solely in an uncaptured owner terminal.

**Existing classic-console bucket:** The qualification bucket was already owner-created; **read back and reuse it** before trying to create another. The classic B2 console may have selected COMPLIANCE even though it displays 30-day Object Lock. Bucket privacy, enabled lock and the duration do **not** establish GOVERNANCE. In an authenticated **local owner** CLI session (never GitHub Actions), use `b2 bucket get <existing-qualification-bucket-name>` and inspect `fileLockConfiguration.value.defaultRetention.mode`, `period` and `isFileLockEnabled`, without publishing the bucket ID. If the mode is already `governance` and the default duration is 30 days, make no change. If it is `compliance` or unset and the bucket is the intended **empty fictional qualification** target, Backblaze documents a scoped correction using the authenticated B2 CLI:

```sh
b2 bucket update --file-lock-enabled --default-retention-mode governance --default-retention-period "30 days" <existing-qualification-bucket-name>
b2 bucket get <existing-qualification-bucket-name>
```

Use a separate account-administration credential for this one-time bucket setting, **not** the five-capability backup uploader key. The second read must show GOVERNANCE, 30 days and Object Lock enabled. Leave lifecycle settings, public access and other buckets unchanged. Do not upload if the post-update readback differs. Source: [Backblaze's October 2026 Object Lock CLI instructions](https://www.backblaze.com/docs/cloud-storage-configure-immutable-storage-for-reseller-and-msp-customers) and [Native API retention readback](https://www.backblaze.com/docs/cloud-storage-enable-object-lock-with-the-native-api).

For the uploader key, the documented B2 CLI form is `b2 key create --bucket <existing-qualification-bucket-name> --name-prefix "qualification/" justelle-qualification-backup listFiles,readFiles,writeFiles,readBucketRetentions,readFileRetentions`. **This command displays its newly created secret**: execute it only in an approved private owner shell with output handled directly into secure secret custody, never a public run, Chat transcript or archived agent log. The routine uploader must not acquire the one-time bucket-administration capability. Verify the effective scope before relying on S3 operations. [Backblaze B2 key CLI documentation](https://www.backblaze.com/docs/cloud-storage-map-iam-policies-and-s3-acls-to-backblaze-b2-access-controls).

**Do not mistake the console's broad Read and Write selection for the required five-capability uploader key.** For exact least privilege, an authorised local owner session can use [Backblaze B2 Native `b2_create_key` v4](https://www.backblaze.com/apidocs/b2-create-key) to make a **standard**, S3-compatible key restricted to the qualification bucket ID and literal `qualification/` object prefix, with only `listFiles`, `readFiles`, `writeFiles`, `readBucketRetentions`, and `readFileRetentions`. An API key name such as `justelle-qualification-backup` avoids unsupported spaces. No `deleteFiles`, `writeFileRetentions`, `writeBucketRetentions`, `bypassGovernance`, unrestricted buckets or master key in the application. Only add an otherwise unneeded bucket-listing permission if a real API compatibility test demonstrates it is essential; document that exception. For the private `JUSTELLE_BACKUP_CONFIG` JSON, set `"prefix":"qualification"` **without** a trailing slash: `scheduled-backup.mjs` appends `/` when constructing object keys, while the B2 application key's `namePrefix` must be `qualification/`. Supplying `"prefix":"qualification/"` fails the runtime configuration check. Verify effective capabilities/prefix and the actual S3 upload, read, retention and clean-restore operations rather than inferring them from a console toggle. [S3 capability mapping](https://www.backblaze.com/docs/cloud-storage-s3-compatible-app-keys).

**Paper recovery-key custody (no USB drive required):** The owner may keep the actual cryptographically generated 32-byte recovery key **on paper in secure physical custody**, entirely outside Firebase and B2. It must be a **Justelle recovery key**, not a Backblaze master/application key, password or chosen phrase. Its printed representation must be either **64 hexadecimal digits** (spacing/hyphens acceptable) or **44 canonical Base64 characters**; those represent the same 32 raw bytes. Keep it in a sealed secure place; never photograph, paste, print to a captured console, upload or store it in a public/synchronised file. The helper can read it directly from this paper, so no encrypted USB drive or persistent digital key file is required.

**One-time owner-local bootstrap:** After personally verifying secure paper custody, use an uncaptured **owner-controlled Windows PowerShell** session (not Codex's agent terminal, Cloud Shell or a GitHub Action), signed into the existing B2/GCP sessions. From the `private-app` directory:

```powershell
node tools/bootstrap-b2-secret.mjs --paper-key --endpoint "https://s3.<actual-b2-region>.backblazeb2.com" --offline-custody-confirmed
```

Replace the endpoint placeholder with the actual private bucket S3 HTTPS endpoint shown in Backblaze. If the existing qualification bucket has the previously permitted short neutral suffix, add `--bucket "<actual-justelle-qualification-backups-suffix-name>"` to select that existing bucket; without `--bucket`, the helper keeps the original exact qualification bucket default. The two environments cannot select one another's bucket. The command does **not** contain the recovery key; it prompts twice with characters hidden and validates exact byte length and matching entries **before issuing a new B2 key**. Neither entry is echoed, entered as PowerShell history or written to an intermediate recovery-key file. A 32-byte key whose bytes differ from the printed copy cannot decrypt later backups, so correct transcription matters. Cancel with Ctrl+C if uncertain, and do not guess the content.

For an alternative offline file on encrypted removable media, the existing `--offline-key "<absolute-owner-held-file>"` mode remains available instead of `--paper-key`; use exactly one. In both modes, the helper uses the already authorised B2 CLI and Google Cloud CLI, checks pre-existing keys and Secret Manager versions, creates a strictly bucket/`qualification/`-scoped five-capability uploader, captures its one-time secret in process memory, and streams `JUSTELLE_BACKUP_CONFIG` into Canada-region Secret Manager through `--data-file=-`. It attempts B2 key revocation on failed installation; verify effective state privately before any retry. Neither successful bootstrap nor copied paper counts as real restoration.

**Separate production backup bootstrap (only after fictional qualification):** The source-tested helper also accepts a tightly scoped production target, but it does not create a bucket or certify its retention. First establish and privately read back a **different private, Object Lock-enabled production bucket** with an approved GOVERNANCE default; name it `justelle-production-backups` or that prefix followed by a short neutral suffix. Keep the production uploader and recovery material in separate owner-controlled custody rather than copying the fictional project's Secret Manager configuration. In an uncaptured owner-controlled PowerShell session, with the proper production B2/GCP administrative sessions, use the same hidden paper-key input with `--target production --bucket "<actual-production-bucket>"` in addition to the existing `--paper-key --endpoint "<actual-B2-S3-HTTPS-endpoint>" --offline-custody-confirmed` options. This writes only `JUSTELLE_BACKUP_CONFIG` in **justelle-production** and requires the production bucket and `production/` object-prefix scope; any qualification bucket or other project is refused. Verify actual production secret IAM, uploaded-object retention, protected backup, independent paper-only restore and alert delivery before real member records are admitted. Never perform this step in an agent-captured shell or treat a successful secret install as recovery proof.

**Independent restore using only the paper:** After a real encrypted `.jmb` version has been uploaded, its retention verified and that ciphertext downloaded to a protected owner-controlled local path, perform an additional clean offline drill **without retrieving the stored Google Secret Manager key**:

node memory/backup-cli.mjs restore-paper "<private-downloaded-archive.jmb>" "<new-private-restore-directory>"

This also prompts for the printed key twice with no terminal echo, then authenticates and restores the archive without writing the key to disk. Verify the expected canonical records and exact source originals against the qualified fictional snapshot; this demonstrates that the independently stored paper can actually recover the encrypted backup. Do not put the encrypted download or recovered contents in GitHub, public logs or shared directories. Keep the original paper securely held after testing. Only run this with the owner at a private TTY. No new provider/service or recurring manual step is introduced.

## Private configuration

**Readiness flags are non-secret repository-level Actions variables.** `JUSTELLE_HOSTED_CONFIGURED` and `JUSTELLE_INITIAL_ACCEPTANCE` are read through `vars.*` in the **job-level `if` conditions** of `.github/workflows/justelle-private-app.yml`, before GitHub starts a job in a named environment. Define them under the repository's **Settings → Secrets and variables → Actions → Variables**, **not only inside an environment**: environment-level variables do not become available until the runner declares that environment, so a job-level guard could otherwise silently skip qualification or production. Leave them unset until the corresponding evidence exists; never set `JUSTELLE_INITIAL_ACCEPTANCE=verified` merely to unblock a workflow. See [GitHub's `vars` context timing](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts#vars-context).

The `justelle-qualification` and `justelle-production` GitHub environments each need these separate secrets:

- `JUSTELLE_WIF_PROVIDER`, `JUSTELLE_DEPLOY_SERVICE_ACCOUNT`, `JUSTELLE_DEPLOY_CONFIG`.
- Qualification also needs `JUSTELLE_QUALIFICATION_SERVICE_ACCOUNT` and `JUSTELLE_PROJECT_ID`.

`JUSTELLE_DEPLOY_CONFIG` is JSON with `mode`, `projectId`, `otherProjectId`, `site`, `origin`, `roomId`, `apiKey`, `gatewayServiceAccount`, `backupServiceAccount`, and `members` (two private email/password credentials for authenticated checks). Qualification additionally has `outsider` (fictional email/password) and `aiPricing`. Do not put actual values in this public repository, issues, screenshots or Actions output. The runner generates ignored `.env.<project>` and `.firebaserc` files at deployment time. Build public Firebase configuration contains no provider credential or personal record.

`JUSTELLE_BACKUP_CONFIG` is private JSON with `endpoint` (the B2 S3 HTTPS endpoint), `bucket`, `keyId`, `applicationKey`, `prefix`, and `recoveryKeyBase64`. The scheduled backup uses a separate identity and performs encrypted upload, per-object governance-retention verification, download checksum comparison and one complete independent restore of the downloaded object before reporting success. The worker also fails before reading Firestore if the configured B2 bucket/prefix belongs to the other environment; this complements, but does not replace, provider IAM and actual restoration verification. Monitor its sanitized `encrypted_backup_failed` event through private Cloud Logging alerting. Configure failure delivery to the owner, and test an actual scheduled run and failed run. Full scheduled snapshots are bounded to 128 MiB in this qualified first implementation; exceeding that limit fails visibly and requires capacity/retention changes. Independent offline recovery remains available through the provider-neutral CLI.

Before deploying, the hosted qualification job runs a read-only `firebase hosting:sites:list` check using the existing deployment identity. It compares the private site value and project to the Hosting site inventory in memory and emits only a fixed readiness code; it does not create a site or stage runtime files. This uses `firebasehosting.sites.get`, included in the existing Firebase Hosting Admin role.

Set `JUSTELLE_HOSTED_CONFIGURED=true` only after identities, project alerts, secrets, IAM and site targets exist. The workflow then deploys qualification following source/browser checks and affected Windows checks and runs real protected HTTP/Firestore tests, live image-aware AI, protected planning screenshot-to-preview/clarification, explicit member Apply/Undo with retained originals, immediate planner edits/history and protected booking originals, revocation, B2 upload/download and offline restoration. The real vision acceptance uses **two distinct synthetic, privately stored red/blue PNG samples with identical prompts** and requires the model to report the actual colour of each; a generic clarification cannot pass as proof of image interpretation. These are scoped paid model calls within the approved ledger and must be accounted for at initial/provider qualification. This tests pixel input, not actual iPhone HEIC decoding or a supplier-confirmed booking. It never runs against the production room. Qualification credentials and diagnostics are ephemeral and are not uploaded as artifacts.

Set `JUSTELLE_INITIAL_ACCEPTANCE=verified` only after hosted qualification, independent recovery, actual scheduled backup/failure checks, a real cloud rollback drill, and both actual iPhones have passed `iphone-acceptance.md`. This is a one-time evidence gate, not a renewed spending or publishing approval. Future authorised `main` changes automatically run appropriate checks, deploy, smoke-check two **distinct authenticated Firebase member UIDs** (not just two credential entries), and record the known-good source. The initial evidence flag is reused, not a recurring approval. The workflows exist in source but are not represented as configured or active until that evidence exists.

| Access, canonical data/history, recovery, providers, dependencies, deployment or unknown runtime paths | Source/emulator/browser plus isolated hosted qualification before production | Unaffected hardware/account setup |
| Local preview runner/dependencies | Windows lifecycle in addition to relevant source checks | Unaffected cloud and phone baseline |

`scripts/release-scope.mjs` is a conservative path list, not a new approval system. Manual workflow dispatch selects full checks. Production also compares all changes since its last verified source and refuses to skip hosted checks if an earlier sensitive change remains undeployed. After that refusal, run the full workflow on `main`; do not reset acceptance flags or bypass the failed check. Failed/cancelled checks cannot release. PR checks use no cloud credentials. Superseded PR checks cancel; in-flight production releases do not.

One-time gates have narrow purposes: `JUSTELLE_HOSTED_CONFIGURED` records provider/configuration readiness; `JUSTELLE_INITIAL_ACCEPTANCE` records established hosted/recovery/device/cloud-rollback evidence. Keep both until established; do not toggle for ordinary releases. Reassess affected evidence after permission/schema/provider changes, actual recovery failure or platform regression. Never claim a skipped check passed.

For a temporary release pause, set the repository Actions variable `JUSTELLE_HOSTED_QUALIFICATION_HOLD` to the exact value `true`. On non-pull-request workflow runs using a revision with this guard, it skips hosted qualification before authentication or provider commands, reports **held (not run)** in a separate job and summary, and blocks the production-release job even if initial acceptance is already verified. It records no qualification evidence and does not change either readiness gate. Source, browser, archive, Rules and preview checks continue normally. This is not a global kill switch: it does not cancel an active qualification/release and does not affect reruns of older workflow revisions or dispatches using refs that lack the guard. While held, do not rerun an older workflow run or dispatch an older ref. To resume, remove the variable or set it to `false`, then use the established workflow and gates. Review and set the hold before merging workflow changes that require hosted qualification; never set `JUSTELLE_INITIAL_ACCEPTANCE` to avoid a qualification run.

## Rollback and failure reporting

The production deploy runner stores only the verified source SHA in the private Firestore operations document. On a deployment or smoke failure, it rebuilds/redeploys the previous SHA, including Functions and Rules, and verifies that version. It never restores old private data or erases subsequent conversations. Hosting's pinned function revision keeps static code and the request gateway together. The scheduled function is also redeployed from the same prior source. Backward-compatible record formats are required for releases; destructive migrations need a separately prepared recovery plan.

A first-release failure has no prior version: the runner removes public invocation from the gateway and disables the new private Hosting site. A failed rollback is reported explicitly as requiring immediate operator attention. Source tests cover these orchestration paths; they do not qualify actual cloud rollback. Verify both success and failure in the fictional project before setting the initial acceptance flag. Actions provides sanitized summaries and failed-job notifications; confirm the owner's notification delivery independently. No private diagnostics or member content should appear in public artifacts.

After hosted acceptance, run the one-time cloud recovery drill from a checkout with full Git history and installed `private-app` dependencies, using the qualification deployment identity and external qualification config:

```sh
node hosting/deploy.mjs /private/path/qualification.release.json qualification-drill <previous-40-character-source-sha>
```

Run from `private-app` in the established deployment environment. Choose a distinct compatible ancestor with the current smoke routes and record format; fetch it before the drill. The currently hosted qualification service must already pass smoke checks at the checkout's `HEAD`. The drill accepts only `hosted-fictional`, `fictional-room`, separate project IDs and the configured site's matching `web.app` origin. It deploys exact commits in temporary worktrees, verifies the prior source, then injects a failure after the candidate's real smoke check to exercise the same automatic rollback orchestration as production. It next exercises first-release shutdown and requires HTTP 403/404 for both Hosting and its health route. Finally it redeploys and smoke-checks the starting `HEAD`, including after a failed drill. A failed restoration reports `qualification-drill-recovery-failed` and requires operator recovery; never treat the attempted restoration as successful. No production acceptance flag or persistent release-state document is changed. Keep the sanitized status and both source SHAs as evidence; source tests alone do not qualify this drill.

The hosted acceptance runner's direct backup/restore call uses the qualification operator. Separately verify the deployed scheduler and backup identity, actual scheduled success/failure, and owner notification delivery. Runtime validation errors emit the same sanitized backup-failure event; monitoring must also detect invocation/platform failures or missing successful backups that prevent application logging.

## Verification boundaries

Source/adapter tests, official emulator Rules tests, isolated Functions-package loading/HTTP checks, the build, and preview lifecycle are available. The production runtime uses only `app.justelle.life`; qualification uses an isolated `web.app` project. The source bundle includes all local imports within the declared Functions `main`, with a locked Functions dependency manifest and a mandatory predeploy rebuild.

No hosted pass, actual B2 storage/restore, provider billing/IAM setup, live AI call, cloud rollback or physical iPhone result is established by those local checks. The hosted acceptance runner must be run after provider access. Merge verified source independently of cloud activation. Keep production disabled until initial launch requirements pass; then deploy under the existing authority without asking to go live again.
