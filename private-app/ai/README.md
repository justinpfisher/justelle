# Replaceable image-aware adapter preparation

**Current product/selection authority:** [Adventure Planner V1](../../docs/ADVENTURE-PLANNER-V1.md) and [Build, Borrow and Replace](../../docs/BUILD-BORROW-REPLACE.md). Future AI work should accept structured scoped adventure snapshots, return typed, Justelle-validated edits or source-backed suggestions, and preserve original provenance; the model never writes directly to Firestore. Personalized **on-demand web research** is a product requirement, but this existing adapter deliberately has **no web search tools** and the old model-only budget does not automatically fund search. Research provider, privacy, pricing, terms and cost enforcement require separate qualification before use.

`vision-provider.mjs` prepares an OpenAI Responses adapter behind the same `respond()` contract as the local deterministic provider. The local preview uses the deterministic provider. The hosted gateway implements the approved vision-provider wiring; actual credentials and live calls remain unverified. Tests use a fictional model, fictional key and injected HTTP responses exclusively.

Activation uses the existing October 13 account/model allowance in [the continuing decision](../../docs/production-launch-decision.md), verified permission for the source discussion, current approved CAD model pricing, token limits and a persistent budget ledger. It sends only the selected discussion and verified PNG/JPEG bytes; a HEIC original remains in Justelle storage while a verified JPEG derivative can be used for interpretation. There are no tools, provider-owned conversation IDs, automatic generation retries or agreement-write capabilities. Strict output validation permits only a reply and an optional suggestion.

[Official vision documentation](https://developers.openai.com/api/docs/guides/images-vision) describes image inputs; [structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs) supplies the response shape; [input token counting](https://developers.openai.com/api/docs/guides/token-counting) supplies the preflight request. `store:false` avoids opting into provider response storage; it is not a promise of zero provider retention.

`FirestoreBudgetLedger` atomically reserves the full input/output cost ceiling against daily and monthly CAD allowances before generation. Reservations survive process recreation. Concurrent requests cannot spend the same remaining allowance. Uncertain failures retain the reservation and refuse automatic repeats; successful completed receipts replay without a second generation. Period boundaries use America/Toronto. The provider cannot reset these private, server-owned counters.

**Before activation:** verify the already-approved model/account and current CAD pricing (including exchange-rate margin and tax treatment), verify token-count payload compatibility and live usage accounting, connect a protected hosted gateway, enforce request-rate/resource limits, grant least privilege, and qualify HEIC derivatives. The ledger is an application-level control, not a cap on all Firebase or unrelated provider spending. The hosted gateway wiring is implemented in `hosting/functions/index.mjs`; local preview remains deterministic. Live image interpretation and web research remain unverified; browsing tools are intentionally absent in this first adapter.
